# Argus Math 迁移到 ts-core

2026-11-09 · 依据 [MATH_SPEC.zh-CN.md](MATH_SPEC.zh-CN.md) 0.7 版

## 为什么要迁

过去三个月，Argus Math 跑在一套 19 万行的 Python runtime 上，用它处理了 OpenAI 论文集的 373 个家族和 84 个开放问题。数学上的收获是真的：134 个家族对 OpenAI 的结论有改进，229 个家族独立复核了原文，还写出了约 12 万行能编译通过的 Lean。但这套 runtime 一边产出成果，一边也在制造麻烦。

最贵的麻烦是**停不下来**。一次调用可以连续跑上千轮，一次运行可以跑五天；Planner 交不出合格的输出，就一遍遍重来，最多一次重试了 532 次。84 个开放问题一共花了一万四千多美元，其中将近三分之二花在少数几次失控的长循环上。

更隐蔽的麻烦是**说不清**。同一条结论在七八个地方各存一份，谁说了算并不清楚；账本不记录一条结论到底出自 OpenAI 原文，还是 Argus 自己的设想，结果 Argus 推翻了自己的捷径，后来被汇总成了"OpenAI 的论文有错"。报告则是写给机器审阅者看的：内部编号、范围声明、免责说明层层叠叠，领域专家读不下去。spec 的初心是"帮助人类专家读懂这些论文"，这一点几乎没有做到。

这些问题不是零星的 bug，而是这套 runtime 的结构造成的：它想做所有领域的通用平台，数学只占其中很小一块；状态、门禁、阶段、自我修复机制层层叠加，每一层都在打补丁，修补前一层留下的问题。在这样的代码上继续修补，修不完，也收不拢。

ts-core（`lbx154/Argus` 的 `feat/ts-core` 分支）是 Argus 的新内核。核心代码不到一万行，它的设计原则正是从上面这些教训里总结出来的：

- 角色之间只用信件交接，记录只追加，不另存"最新状态"；
- 运行时只传信、守权限边界，不当家长，也不替 Agent 做科研判断；
- Reviewer 亲自重跑关键检查，并把"人读着累"当成和错误同等的问题退回。

Argus Math 应该搬到它上面去。

## 搬过去之后，一篇论文是怎么被处理的

以一个 OpenAI 家族为例。

运维把任务交给 Manager：处理哪个家族，原文在哪里。任务不大时，Manager 直接交给一个 Engineer；一个家族有好几篇论文时，由 Planner 拆开，交给几个 Engineer 并行处理。

Engineer 的工作是**读懂这篇论文，并让别人也能读懂**。它先通读原文，找出主定理和撑住主定理的几个关键步骤，在这几处下功夫：

- 能用 Lean 写下来的写成 Lean；
- 能算的就写成可复跑的计算；
- 原文一笔带过的地方，把论证补完整。

在这个过程中，它可能发现原文的问题，也可能发现原文的结论可以做得更强。最后它交出一份**读懂报告**：

- 第一句话说结论：成立、有错、有缺口，还是在原文基础上有了改进；
- 接着讲清楚这篇论文在做什么、证明的主线是什么、难点在哪里；
- 然后才是细节：补上的步骤、核过的部分、发现的问题或改进；
- 每一处都指回原文的位置。

Reviewer 拿到报告时，**假装自己是一位没读过这篇论文的同行**。它要回答两个问题。第一，结论对不对：它会亲自重跑关键的 Lean 和计算，检查每条"原文有错"是不是真的针对原文，而不是针对 Argus 自己提出的设想。第二，能不能读懂：一位领域专家照着这份报告，能不能在一刻钟内抓住主线，在一小时内自己核一遍关键步骤。有一样做不到，就退回重写。

报告通过后，Manager 把结论写成一封信交给运维，附上报告和证据的位置。

整个过程中，没有阶段机，没有完成证书，没有额外的裁判。"完成"就是 Reviewer 放行，Manager 写了信。我们相信 Agent 如实报告，不另设门禁。

## 让证明好读，具体要做什么

spec 0.7 版在 §2 里写了"证明要写给人读"的五条要求，迁移时要把它们落到实处，而不只是写进提示词。

**一是改掉写作的出发点。** 旧 runtime 里，Engineer 的报告是写给 Reviewer 验收的，Reviewer 的标准是"证据链是否完整、范围是否标清"。于是报告越写越像法律文书。新的 math 技能里，报告的读者被明确定为"领域专家"，Reviewer 的退回理由里，"读不懂"与"有错"同等对待。ts-core 已经有这条规则（#438），math 技能要把它具体化到数学证明上。

**二是区分原文的论证和补上的论证。** OpenAI 的论文经常跳步。Argus 在核验时往往已经把跳过的步骤补完整了，但旧报告里这些补充混在审计记录中，读者看不出来。新报告里，补上的步骤要单独标出"原文此处从略"，让读者一眼看出哪些是原文、哪些是我们的工作。这本身就是帮助读懂论文的核心贡献。

**三是让 Lean 有人话的说明。** 每份 Lean 证明旁边都放一份陈述忠实性说明，用一两段文字讲清它证了什么、和原文命题是什么关系、没覆盖什么。报告引用 Lean 时引用这段说明，而不是让读者去读 Lean 代码。

**四是不堆免责声明。** "新颖性未核实""这不构成对原文的反驳"这类话，只在真正影响读者判断的地方说一次，不在每一段重复。

**五是给出处，不给编号。** 报告里不出现内部 ID、campaign 编号、claim 编号；指向原文用"第 3 节引理 3.2"，指向证据用文件路径。

## 保留什么，丢掉什么

旧 runtime 里，真正需要带走的只有数学工具，它们继续用 Python 写，做成一个 math 技能包挂到 ts-core 上：

- **Lean 验证**：编译、检查有没有 `sorry` 和自定义公理。不再存哈希，版本交给 git；Reviewer 放行前会亲自重跑报告里引用的 Lean。
- **可复跑计算**：记下命令、输入和输出，任何人能重跑。
- **引用核查**：找到被引的文献，存下相关原文的摘录。只解析到文献存在、没读命题的，不算核过。
- **证明地图 `PROOF.md`，取代账本。** proof_ledger 原本承担两件事：组织证明（目标依赖哪些引理、还差什么），以及记录证据和状态。前一件有真价值，保留下来，改成每个项目一份自然语言的 `PROOF.md`：目标、骨架、每条引理的出处、状态和证据文件、放弃的路线。它同时是读懂报告的骨架。后一件的 JSON 账本不再要，其余记录沿用 ts-core 的信件和记录。"原文有错"必须指向原文里的一句话，由 Reviewer 核对。

其余的一律不带：账本（`MATH_STATE.json`）、证明图、手填的状态、判断类的证据记录、阶段机、完成证书、各种收据和交接文件、框架自修机制，以及与数学无关的领域模块。审阅者的意见写在 Reviewer 的信里，不再抄进账本。

估计 math 技能包的 Python 代码在两千行以内。原来同一块代码有一万行左右，还有一份逐字节相同的副本。

## ts-core 需要补的几样东西

ts-core 的方向是对的，跑数学还要补上几样：

**math 技能包。** 内容包括 `SKILL.md`（写报告的要求和 Reviewer 的验收标准，按上一节展开）、数学工具和 Lean 工具链的安装脚本。ts-core 已经支持技能包自带安装脚本，并会把共享工具放进每个角色的命令路径。

**关掉框架自修。** ts-core 自带 `argus-maintenance` 技能，数学项目里要停用。spec I7 规定 Agent 不修改框架。

**不设交付门禁。** spec 0.8 版取消了 `math check`。放行完全由 Reviewer 判断：它亲自重跑关键的 Lean 和计算，检查每条"原文有错"确实指向原文，并确认报告读得懂。

## 怎么一步步做

**第一步，写 math 技能包，不碰 ts-core 内核。** 把数学工具从旧 runtime 中剥出来、瘦身，写好 `SKILL.md`。这一步在本地完成，不花模型的钱。验收标准是：拿一个已经完成的家族（比如 #127），用新工具重新核一遍它的 Lean 和计算，结果与旧记录一致。

**第二步，小规模试跑。** 挑两三个已经知道答案的家族，比如 #127 和 #332，在 ts-core 上完整跑一遍。看两件事：花了多少钱；报告能不能让一位没读过原文的人读懂。后一件由你或一位领域内的同事判断，不由 Agent 自评。

**第三步，看试跑结果再决定。** 如果试跑的报告确实好读、花销可以接受，再考虑把剩下的家族迁过来。第一轮的底稿和 Lean 已经在 `argus-mathematics` 仓库里，新的处理可以直接从这些材料出发，不必从头再做。

第一步不花 Argus 的模型额度。第二步开始花钱，会单独请你批准。

## 旧数据怎么办

373 个家族的底稿、核查记录和 Lean 都已经发布在 `argus-mathematics` 仓库的 `openai-math/` 下，不随迁移改动。迁移后，新跑的家族在同一位置补上读懂报告。旧的 Lean 和计算可以作为新报告的证据直接引用；旧账本不导入，它的内容已经整理进报告和核查数据。
