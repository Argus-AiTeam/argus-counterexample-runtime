# Argus Math 顶层规格

版本 0.9（§10 第 1、3、4、5 项已定，第 2 项待定） · 2026-11-09

## 0. 本文的地位

本文是 Argus Math 的唯一权威。数学 pack 的 `SKILL.md`、角色提示、campaign 契约（OBJECTIVE/LAUNCH）、
harness 和工具都从本文派生，并标注所依据的条款号。派生物与本文冲突时，以本文为准，派生物要改。

本文只由运维（lbx154）修改。每次修改升版本号，并在文末变更记录里写明改了什么、为什么。
Agent 对本文、数学工具和 Argus runtime 只有读权限。

## 1. 初心（不得更改）

**用 Argus 这套自动化系统，核验 OpenAI 公开的数学论文，并帮助人类专家读懂它们。**

- 范围：`openai/math` 在固定提交 `4eaee87548250b2682affda7d05d947c05554bae` 上的在架稿件，
  共 721 篇，分属 373 个家族。上游另有 3 篇已撤稿（家族 W01–W03），不纳入。
- 核验和讲清楚是基本功，每一篇都要做。在这个过程中：
  - **发现 OpenAI 论文里的错误**（结论错、引理错、反例、引用错）；
  - **发现它们的不足**（缺假设、证明有缺口、表述过强、没交代的依赖）；
  - **在它们的成果上更进一步**（加强、推广、更简单的证明、补上缺口）；
  这三类都是重要成果。
- 没发现问题也是结论，如实写"在已核范围内未发现问题"，并写清核了哪些部分。不为了出成果而制造错误，
  也不把没查过的部分说成核验通过。
- **审查 Argus 留下的旧稿，搞清楚我们到底取得了什么成果**，这本身也是一项交付。每份旧稿逐项判定：
  成立且是原创、成立但只是复现原文、推翻的只是 Argus 自己的攻击、论证不成立、未决。
  旧稿的结论在核对之前只是待查的主张，不是成果。

一般化地说，Argus Math 把一个数学问题变成**别人能独立复核、也能读懂的结论**。

## 2. 交付物

一次交付 = 给运维的一封结论信 + 报告 + 信中列出的证据文件。

结论必须恰好是下列之一，信的第一句写明是哪一种：

| 结论 | 含义 |
|---|---|
| 证明 | 目标命题成立，论证完整 |
| 反例 | 给出满足全部原条件的对象，使目标命题不成立 |
| 限定结果 | 在写明的额外假设或范围内成立；范围逐条列出 |
| 计算证据 | 有限范围内的可复跑计算，不主张普遍成立 |
| 未决 | 没有解决；写明具体卡在哪个命题，以及试过并排除的路线 |
| 审查结论 | 对他人稿件的逐单元判定（见 §5 审查模式） |

**结论必须让人读得懂**（§3 I8）。每份交付给人看的报告：

- 第一句用平实的话说清结论：成立、有错、有缺口，还是未决；
- 原命题照录，并给出在原文里的位置（文件、节号或定理号）；每条结论写明出处：出自原文，还是我们提出的；
  说"原文有错"，必须指向原文里的一句话，而不是我们自己提出的捷径或推广；
- 讲清为什么：证明的骨架、哪几步是关键、核心想法是什么，让领域内的专家不重走全文也能跟上；
- 指出问题时，给出最小的可手算例子或可复跑的计算，并指到具体哪一步；
- 写明依赖的外部结果，以及哪些部分是机器核过的、哪些只是人工判断。

**证明要写给人读。** 机器核过不等于讲清楚了。写证明时：

- 先用几句话说核心想法：为什么这条路走得通，难点在哪里；再给出骨架，最后才展开细节；
- 原文跳过的步骤，补上，并注明"原文此处从略"，让读者知道哪些是原文的、哪些是补的；
- 一步依赖某个引理或外部定理时，当场说清它在这里起什么作用，不只给一个编号；
- 机器核过的部分，用一两句话说清 Lean 实际证明了什么命题，读者不读 Lean 也能明白；
- 改进原文时，把原来的结论和新的结论并排写出，说清改进落在证明的哪一步。

每个结论标出支撑它的证据类型。四类证据互不相加，也没有综合分：

| 证据 | 唯一来源 |
|---|---|
| 机械 | `math lean verify` 编译通过，没有 `sorry`，没有自定义公理 |
| 计算 | 记录了命令和输入、任何人可复跑的计算 |
| 文献 | 读者存档的原文摘录 + 判定 |
| 判断 | 审阅者的意见 |

## 3. 不变量

每条都是硬规则，没有例外，也不允许按项目协商。

- **I1 已证只能来自机械证据。** "已证"只能来自 Lean 编译通过；其余结论如实写明凭的是计算、文献还是判断。
- **I2 陈述忠实性单独成文。** 形式陈述和原问题是否等价，写在与 Lean 文件放在一起的单独文档里。
  Reviewer 放行前亲自重跑报告引用的 Lean；版本由 git 记录，不另设哈希。
- **I3 引用指向命题。** 引用写明文献版本和具体定理号；交付前必须有非作者的人读过原文，并存档摘录；
  拿不到原文就明说"无法核对"。
- **I4 不自我验收。** 写结论的人不能核验自己的结论和引用。
- **I5 有限不等于普遍。** 有限计算不能称为普遍证明；扩大验证范围不算缩小与目标的距离。
- **I6 目标归运维。** 任务目标和标准由运维定。Agent 不改写目标、不降低标准；
  发现目标本身问错了，如实报告，由运维决定。
- **I7 不修框架。** Agent 不修改 Argus runtime、本文和数学工具。框架问题写成报告交给运维：
  具体的诊断信息、在哪条事件记录里。
- **I8 人能读懂。** 交付的报告以领域专家能读懂、能复核为标准（§2）。读不懂、找不到依据、
  术语和免责声明堆砌的报告，与错误同等对待，退回重写。

## 4. 宿主、工具、角色的分工

**宿主** 就是 ts-core，只做两件事：传信、守权限边界。记录沿用 ts-core 原有的信件和记录，不另设账本。
宿主不当家长：Agent 自己能做的事（等待、轮询、判断自己是否卡住、决定下一步），宿主不代办，也不设规则预防。
宿主不判断数学，也不拦截交付。我们相信 Agent 如实报告；结论是否成立，由 Reviewer 读论证、重跑关键检查后判断。

**工具** 只陈述机械事实。沿用现有 Python 实现（`argus_skill.verticals.math.*`），下文以 `math …` 简称：

| 简称 | 现有命令 | 做什么 |
|---|---|---|
| `math lean verify` | `python -m argus_skill.verticals.math.lean_evidence verify`（异步版 `lean_async`） | 编译并做公理审计，是机械证据的唯一来源 |
| `math cite` | `python -m argus_skill.verticals.math.citation_check` | 查文献是否存在；存档摘录并记录判定 |

**角色** 的判断：Reviewer 读论证、亲自重跑关键的 Lean 和计算、检查报告能否读懂，决定是否放行；
Engineer 做数学；Planner 拆分路线；Manager 对运维负责。

## 5. 三种模式

campaign 启动时由运维选定，之后不能更改。

| 模式 | 交付什么 | 新颖性 |
|---|---|---|
| 攻关 | 对一个指名的目标命题，给出证明、反例或未决报告 | 主张新结果时必须查证 |
| 探索 | 在指定方向上的限定结果或计算证据 | 主张新结果时必须查证 |
| 审查 | 对给定稿件逐篇核验并写出读懂报告：成立 / 部分成立 / 错误 / 未决，并注明归属；发现的错误、不足和推进单独列出 | 核验本身不主张新结果；"更进一步"的部分主张新结果时须查证 |

## 6. 环境与进程

每个 campaign 是 ts-core 里一个独立的项目，有自己的记录；campaign 之间只通过共享的技能库和 wiki 交换经验。

Lean 工具链和 Mathlib 由 pack 的 setup 安装到固定版本；每次编译记下实际使用的版本。
没有工具链时，不提交 `.lean` 文件，改用文字论证。

## 7. 节约 token

花钱的地方只该是数学本身。下面每条都对应实际发生过的浪费：

- **已知情况查一次**：文献和已知结论在开始时查清，写成共享的笔记（wiki），所有人共用。同一次检索不要每个 worker 各做一遍。
- **复用，不重做**：已经核过、没有变化的结论和计算直接引用，不重新跑；旧稿里核对通过的部分直接复用。
- **只核关键处**：精力放在一旦出错就会推翻主定理的步骤上，常规步骤点到为止。
- **不做无效进展**：扩大有限验证的范围不算进展（I5），不为它花钱。
- **不写过程文书**：不为流程写计划、审计、状态之类的文件；报告每件事只写一次。
- **提示只写模型不知道的**：skill 和契约写经验与约束，不写模型本来就会的东西。
- **不修框架**（I7）：框架问题交给运维，不在 campaign 里花钱自修。
- **按真实计量汇报**：每次调用的真实花销已在 ts-core 的记录里，汇报时按家族列出。

## 8. 不做什么

- 不设阶段机，不设交付门禁；放行由 Reviewer 判断。
- 不评分，不按报告数、文件数或行数计成果。
- 不让 Agent 自修框架，也不让它自己提出部署。
- 不把审阅者的同意算作证明。

## 9. 防止偏移

- 派生物里每条规则标注依据的条款号；找不到依据的规则删掉。
- 每条不变量至少对应一个自动测试；pack 和提示里出现与本文冲突的概念（例如阶段机），测试失败。
- 在 Agent 沙箱里，本文、数学工具和 runtime 只读。

## 已知偏差（现行 runtime 与本文不一致之处）

现行 Python runtime 将迁移到 ts-core（`lbx154/Argus` 的 `feat/ts-core`），方案见
[`MIGRATION_TS_CORE.zh-CN.md`](MIGRATION_TS_CORE.zh-CN.md)。迁移完成前，下列偏差仍然存在：

- 现行 runtime 自建账本（`MATH_STATE.json`、`PROOF_GRAPH.json`、证书和收据）并用哈希绑定版本，与本文 §4、I2 不一致；
  迁移后不再使用，记录沿用 ts-core。
- 现行报告不写结论的出处，曾导致 Argus 推翻自己的捷径被汇总成"原文有错"（§2 现已要求逐条写明出处）。

- 现行 Python runtime 有 `math check` 交付门禁，以及另一层研究目标完成检查（结果类别、新颖性、最终认证收据），
  由 `argus_skill/core/research_contract.py` 和 Manager 完成判定执行。它们与本文 §4"宿主不拦截交付"不一致；迁移时删除。
- 审查模式（§5）在现行 runtime 中借用 `exploratory` 目标级别运行，靠 campaign 契约说明新颖性填
  `not_applicable`；尚未成为独立模式。

- 9200 轮最初的契约（`counterexample_harness/old_draft_review_objective.md`）只要求审查 Argus 自己的旧稿，
  偏离了 §1 初心。2026-11-07 起，未完成的 322 个家族已切换到 `counterexample_harness/openai_family_objective.md`；
  切换前已完成的 51 个家族只做了旧稿审查，没有逐篇读懂报告和核验结论；已定不补做。
